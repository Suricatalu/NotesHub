# notes-to-html

Translates the synced notes under the repo's mirror folders (whatever `dst` values `src/sources.conf` defines — `notes/`, `research/`, `embedded/`, anything) into single-file HTML pages placed in `www/pages/<section>/`.

**This Skill is only responsible for visual presentation.** Page granularity is determined by `src/www.conf`, status detection is determined by `src/www.py`, and the navigation menu is generated by `www.py nav` — none of these three things are managed here, and you should not touch them.

## Execution Flow

```bash
python3 src/www.py status --json          # 1. See which pages need processing
python3 src/www.py plan <page id>         # 2. Get main, refs, note, and out for that page
# 3. Read main (and any needed refs), generate html per this Skill, write to the out printed by plan
python3 ${CLAUDE_SKILL_DIR}/scripts/validate_page.py <the html just written>  # 4. Validate
python3 src/www.py commit <page id>       # 5. Write back to the manifest
python3 src/www.py nav                    # 6. Regenerate the nav menu after all pages are processed
```

Page id is `<section>/<md filename>`, and the output path is fixed as `www/pages/<section>/<md filename>.html`. This path is derived — `www.conf` has no field to specify it. **Use the `out` line printed by `plan` directly**; do not assemble it yourself.

> **Two words that are easy to confuse.** A **section** is a `[bracketed]` block in `www.conf` — a named group of pages, and the first component of the page id. A **heading** is a markdown heading inside a note. The structure rule below is about *headings*; it says nothing about sections.

`plan` and `commit` also accept a section name, meaning "all pages under that section", but **only generate one page at a time** — do not cram multiple pages into the same file.

Rules:

- **Only process `NEW` and `STALE:*`.** Skip `OK`.
- **Always stop and ask the user when you encounter `DIRTY`** — do not overwrite it directly; that html has been manually edited.
- **For `ORPHAN` and `MISSING:src`, only report them — do not delete files or edit the conf yourself.**
- **Do not commit if validation fails.** If `validate_page.py` reports a FAIL, fix the html first.
- **Never hand-write `manifest.json`.** The hash will be computed incorrectly, and it's a pure waste of tokens.

## One Main File = One Page

`plan` gives you two kinds of sources, which are fundamentally different in nature:

| | Role |
|---|---|
| `main` | **The body of this page. One md maps to one html, one-to-one.** The heading structure is inherited directly from it |
| `refs` | Supporting evidence. Used for looking up terms, getting numbers needed for diagrams, confirming context — **not a source of content** |

**The heading structure of `main` must not be altered.** Specifically:

- The **order** of headings follows the original text; do not reorder them;
- The **level** of headings follows the original text; do not change H2 to H3, and do not merge two headings into one;
- **Do not add headings that aren't in the original**, and do not delete headings that are in the original;
- The heading **text** may be polished for readability (adding an implied subject, removing numbering), but its meaning must not be changed.

The heading structure is determined by the md, not by you — **your job is to do a visual translation on the existing skeleton, not to rewrite the table of contents.**

**This constrains you, not the notes.** The rule does not freeze the page: when `main` itself gains, loses or reorders a heading, its hash changes, `www.py status` reports the page `STALE:src`, and regenerating produces a page with the new structure. That is the intended — and only — way a page's table of contents changes. What is ruled out is the *page* having a structure that `main` does not have, because then nobody could say where that structure came from.

There are only three uses for `refs`: verification, filling in terms that `main` refers to but doesn't expand on, and getting the correct values or process when drawing a diagram. **Content from refs does not spawn headings of its own.** When a citation is needed, place it in the body text under an existing heading, in a glossary card, or in a pitfalls note, and mark it as a reference in the "Sources for this page" block.

The refs given by `plan` may include the `main` files of other pages in the same section (this happens when the `refs` glob scans the whole directory — your own main has already been excluded). **Those are sibling pages; when referencing them, use a relative link to point to them** — do not copy their content in, as that would again turn into merging multiple md files into one page.

## Four Contracts (`validate_page.py` checks each one)

1. **Self-contained single file**: must not reference any external CSS / JS / font / image. Every page must be openable on its own and able to be sent to a colleague standalone.
2. **Must have a "Sources for this page" block**, linking back with relative paths that must resolve on the filesystem. **The main file must be marked `<li data-role="main">`, exactly one per page**, and references marked `data-role="ref"`. Readers use this to know which file is the body of this page and which document the heading structure should map back to; see [`references/components.md`](references/components.md) for the syntax.
3. **Must not read or write `manifest.json`.**
4. **Must work correctly both inside an iframe and when opened standalone.** Pages live inside an iframe in `www/index.html`.

Contract 1 has two direct corollaries — do not try to work around them:

- **Do not use mermaid.** It would need to be vendored into the repo (adding several MB per page) or loaded via CDN (which violates offline use). Diagrams must always be hand-written inline SVG.
- **Do not use KaTeX / MathJax.** They require bundling font files. Math expressions must always use **MathML**, which browsers support natively with zero dependencies.

## How to Produce a Page

**Copy a fresh version of [`assets/page-template.html`](assets/page-template.html)**, and replace the `<<< >>>` placeholder markers. Leave the CSS and JS untouched — they are the source of site-wide consistency. When a new style is needed, add it to the skeleton first, then sync it to existing pages.

### Translation, Not Transcription

md is linear text; a web page is made of structured components. The value of this layer lies in the mapping, not in making it look pretty. **The mapping happens under a heading**: the heading sequence is laid out exactly as in main — it's the content under each heading that you reorganize.

| When the md looks like this | It should become |
|---|---|
| A sequence of "first... then... next..." | Trust-chain diagram / flowchart |
| Partition tables, offset lists, memory maps | Storage layout diagram / address space diagram |
| Nested "if X then Y, else Z" | State machine |
| A discussion of the pros/cons of two or three options | Decision matrix |
| A bunch of benchmark numbers | `scripts/make_chart.py` |
| Derivations, formulas | MathML + symbol table |
| A term that appears 1–3 times | Glossary card |
| "This is where I got stuck" | Pitfall note (`.pit`) |

Rule of thumb: **draw a diagram when there are three or more parallel items, or two or more state transitions. Do not draw a diagram for a relationship between just two elements** — a single sentence is faster.

### When Material Is Insufficient

For anything main doesn't cover, **do not fill it in with your own prior knowledge**. Readers assume every sentence comes from those notes; mixing in unlabeled model knowledge is the most serious failure mode of this process, and it's completely invisible on the surface.

Order of handling: **check `refs` first** → note it under "Not covered" → ask the user → only search the web if truly necessary.

Content found via web search must be explicitly marked in the text as not coming from the repo's notes, and the URL must be listed in the "Sources for this page" block. Supplementing with external data **may only enrich what sits under an existing heading, and must not create a new heading as a result** — that would amount to altering main's structure with external knowledge.

The `note` field in `www.conf` is extra instructions given by the user, applying to every page in that section, and must be followed.

## Three Non-Negotiable Visual Rules

### 1. Diagrams Never Scale Up, and Never Shrink Without Limit

```
Effective font size = SVG nominal font size × (container width ÷ viewBox width)
```

Every `<svg>` **must carry its own** `style="--fig-vb:<viewBox width>px"`:

```css
.fig-frame svg    { max-width: var(--fig-vb); }  /* never scale up */
.fig-scroll > svg { min-width: var(--fig-vb); }  /* scrollable type never shrinks */
```

There's no build step to inject this for you — omitting it means `width:100%` scales the diagram up to the container width, and the font size balloons proportionally along with it. **This is the easiest mistake to make and the hardest to spot visually**; check `[D]` catches it.

Size limits (derivation in `references/rwd.md` — since the iframe is narrower than the viewport, the numbers differ from a typical website):

| viewBox width | Strategy |
|---|---|
| **≤ 740** | `fig-scroll`, fixed 1:1 ← **the default. Set the canvas to 740 from the start** |
| 741–900 | Still 1:1, but **it will scroll horizontally on a laptop**; `[E]` emits a WARN |
| > 900 | Split into a wide variant (≤ **740**) + narrow variant (≤ **340**) |

**740 and 900 govern different things**: 900 guarantees the font size won't break (a scrolling diagram never scales down anyway), while 740 guarantees **no scrolling is needed** — at the breakpoint where the in-page table of contents appears (iframe 1100), the container is only 748. A diagram that looks like a perfect fit on your own large monitor will scroll sideways on the reader's laptop.

The order for reducing width is fixed: **change direction → reduce density → split the diagram → only then build dual variants**. **You may not shrink the font size to buy width** — 9.5px is the accessibility floor.

### 1b. A Diagram May Carry Only One Edge Semantic

Before drawing, write out in one sentence: "the arrows in this diagram mean ______". **If you can't write a single sentence, the diagram should be split in two.**

When a second kind of relationship genuinely has to appear in the same diagram, **change the line style (dashed) and spell it out in the legend** — both, not either. The first item of `.legend` must be the edge semantic, with colors listed after it — `[L]` enforces this (only required when the diagram actually has arrows).

The failure mode that is hardest to spot yourself looks like this: the boxes are drawn beautifully and every arrow is a solid line, but one of them means "A produces B", another means "you copy this by hand", and a third means "the build packages it in". Faced with three identical arrows, readers can only guess — and they frequently guess "converging arrows = union of the two sources", which is usually wrong.

### 2. Anything Hidden via CSS Must Have Corresponding Validation

The two variants must be written as `.fig-frame svg.only-wide` (specificity 0,2,1) to override `.fig-frame svg` (0,1,1). Writing it as just `.only-wide` (0,1,0) gets overridden — both variants render at once and the narrow one gets stretched to full width. **Specificity outranks source order, and a media query won't save you** — and it reports no error at all. The skeleton is already written correctly; do not change it.

### 3. Long Formulas Must Scroll on Their Own

Every display equation is wrapped in `.math-scroll`. MathML does not wrap automatically, so a long formula will stretch the entire page layout wider, distorting every paragraph along with it. It's invisible on desktop but a disaster on mobile.

## Validation Checks

| | Check |
|---|---|
| A | SVG elements must not exceed the viewBox |
| B | Hard-coded color codes are prohibited inside SVG |
| C | The figure six-piece set: figure number / title / legend / caption / text equivalent / aria-label |
| D | `--fig-vb` equals the viewBox width |
| E | Effective font size ≥ 9.5px at the worst-case iframe width; scrolling type with viewBox > 740 emits a WARN |
| F | In-page anchors resolve correctly |
| G | Color contrast meets WCAG AA (both light and dark color schemes) |
| H | SVG text must not overflow its box (including CJK full-width characters) |
| I | CSS specificity for switching between the two variants |
| J | Glossary cards correspond to the embedded glossary and have a source |
| L | When a diagram has arrows, the legend must state what the arrows mean (**FAIL**, no exceptions) |
| K | Data charts have units / sample size / error definition / method / source / raw data |
| M | MathML structure, scroll container, symbol table |
| N | Offline self-sufficiency (Contract 1) |
| O | Sources for this page exist, paths resolve, and the main file is marked (Contract 2) |
| P | iframe compatibility, manifest untouched (Contracts 3, 4) |
| Q | No `<<< >>>` placeholders left unfilled (**FAIL** — running it on the skeleton itself is recognised and skipped) |

## Write Back Lessons Learned from Pitfalls

D, E, H, I, N, and O are all checks that were added because they were actually hit during implementation — not ones thought up in advance.

When you encounter a new failure mode: **first add a check that will FAIL → run it once against the old approach to confirm it catches the issue → then fix the skeleton**. Doing it in the reverse order often results in a check that fails to catch the original problem.

The validator itself can also break, and it's harder to notice — when it breaks, it reports PASS instead of an error. There was once a case where the text `<svg>` appeared in a CSS comment, and the regex for matching SVG started matching from the comment and swallowed the entire CSS block, silently causing four checks to fail to catch anything. Always run regression tests after modifying `validate_page.py`.

**Note**: changing any file inside this Skill folder will change `skill_sha`, turning every page into `STALE:skill`. If the change is to an unrelated part of the Skill (e.g., only a comment was changed), use `python3 src/www.py accept-skill` to update the hash without triggering a full site regeneration.
